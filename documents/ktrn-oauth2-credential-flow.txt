KTRN GATEWAY (192.168.21.7:8086 / cloud/ktrn/bss) - WHERE CREDENTIALS GO
==========================================================================

Context: the gateway's OpenAPI document (GET /cloud/v3/api-docs) exposes a
securityScheme of type "oauth2", flow "password", pointing at:

    tokenUrl: http://mint-gateway:9999/admin/oauth2/token

This means two separate HTTP requests are involved, and credentials are
carried differently in each one. Worked example below uses the balance
search operation (svccode HP00001 / opcode HPOP001) since it's the one
already fully implemented and tested on our side.


1. GETTING A TOKEN (one-time / periodic - not sent on every business call)
----------------------------------------------------------------------------
Standard OAuth2 "password" grant. Credentials go in the REQUEST BODY,
form-urlencoded:

    POST http://mint-gateway:9999/admin/oauth2/token
    Content-Type: application/x-www-form-urlencoded

    grant_type=password&client_id=<CLIENT_ID>&client_secret=<CLIENT_SECRET>&username=<USERNAME>&password=<PASSWORD>&scope=server

OR - the other common OAuth2 convention (RFC 6749 s2.3.1) - client_id and
client_secret go in an HTTP Basic Auth header instead, and only
grant_type/username/password/scope stay in the body:

    POST http://mint-gateway:9999/admin/oauth2/token
    Authorization: Basic base64(client_id:client_secret)
    Content-Type: application/x-www-form-urlencoded

    grant_type=password&username=<USERNAME>&password=<PASSWORD>&scope=server

NEEDS CONFIRMATION FROM THE PLATFORM OWNER: which of these two forms their
server actually expects. Both are standard; only one will match their
config.

Expected response: a JSON body containing an access_token (and usually
token_type, expires_in, refresh_token).


2. CALLING THE ACTUAL BUSINESS ENDPOINT
----------------------------------------------------------------------------
The access_token from step 1 goes in the Authorization HTTP HEADER -
never in the body. The body is unchanged from what the RBSS-CCBS
API_ACCESS documentation already specifies - no credentials in it at all,
just the business XML.

    POST http://192.168.21.7:8086/cloud/ktrn/bss
    Authorization: Bearer <ACCESS_TOKEN_FROM_STEP_1>
    Content-Type: application/xml

    <?xml version="1.0" encoding="UTF-8"?>
    <request>
      <header>
        <svcode>HP00001</svcode>
        <opcode>HPOP001</opcode>
        <CHCODE>A</CHCODE>
      </header>
      <body>
        <MSISDN>0771000050</MSISDN>
        <ISP_CD>62</ISP_CD>
      </body>
    </request>


SUMMARY
----------------------------------------------------------------------------
- Credentials for OBTAINING a token -> request BODY (form-urlencoded),
  or client_id/client_secret via Basic Auth header depending on their
  server's configuration (needs confirmation - see above).
- The TOKEN itself, on every subsequent business call -> Authorization
  HTTP header, as "Bearer <token>". This part is standard OAuth2 and not
  specific to their system.

What we need from them to proceed:
  1. client_id
  2. client_secret
  3. a service-account username
  4. that service account's password
  5. confirmation of scope = "server" (seen in their schema) is correct
     for this integration
  6. confirmation of which of the two token-request forms above their
     server expects
